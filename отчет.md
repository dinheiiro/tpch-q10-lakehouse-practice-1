## 2. Поднятые сервисы — и почему именно они

| Сервис | Зачем нужен |
|---|---|
| RustFS | Совместимое с S3 хранилище файлов; бакеты `bronze`, `silver`, `gold` разделяют слои физически. Я использовала его, потому что публичный образ MinIO не скачался при развёртывании. |
| PostgreSQL 17 | Хранит служебные данные каталога Lakekeeper. |
| Lakekeeper | REST-каталог Iceberg: три warehouse указывают на три разных бакета. |
| Trino 476 | Генерирует `tpch.sf1`, создаёт Iceberg-таблицы и выполняет контрольный и измеряемые запросы. |
| Superset 6.0.0 | Отдельное приложение для просмотра Bronze через Trino в SQL Lab. |

Я запускала стенд из корня репозитория в PowerShell:

```powershell
py scripts/setup.py prepare
$runtime = 'D:\lakehouse-tpch-q10-runtime\runtime.env'
docker compose --env-file $runtime config --quiet
docker compose --env-file $runtime up -d s3 postgres lakekeeper
py scripts/setup.py bootstrap --accept-lakekeeper-terms
docker compose --env-file $runtime up -d --build trino superset
docker compose --env-file $runtime ps
py scripts/run.py
```

`prepare` создаёт случайные пароли в частной папке на D:, вне Git. После подтверждения условий Lakekeeper я создала три warehouse. На этом запуске все стандартные порты были свободны: S3 API — `http://127.0.0.1:9000`, консоль RustFS — `http://127.0.0.1:9001`, PostgreSQL — `127.0.0.1:5432`, Lakekeeper — `http://127.0.0.1:8181`, Trino — `http://127.0.0.1:8080`, Superset — `http://127.0.0.1:8088`. Подтверждения: [контейнеры Docker](evidence/docker-services.jpg), [три бакета RustFS](evidence/rustfs-three-buckets.jpg), [список бакетов](evidence/buckets.txt).

## 5. Тесты производительности

Я записала одинаковые полные таблицы четырьмя способами. Время записи — сумма четырёх `CREATE TABLE AS SELECT`; время чтения — от отправки Q10 до получения всех страниц результата. Для каждого набора сделала один прогрев и пять последовательных измерений. Размер — сумма `file_size_in_bytes` из Iceberg `$files` текущего снапшота, без старых и служебных файлов. Исходные числа и ID запросов сохранены в [measurements.json](results/measurements.json).

| Формат/кодек | Строк | Размер, МБ | Запись, с | Прогрев, с | Пять Q10, с | Медиана, с | Мин., с | Макс., с | Расхождения |
|---|---:|---:|---:|---:|---|---:|---:|---:|---:|
| Parquet/GZIP | 7 651 240 | 193.836 | 21.712 | 1.188 | 1.223; 1.014; 1.094; 1.166; 0.927 | 1.094 | 0.927 | 1.223 | 0 |
| Parquet/ZSTD | 7 651 240 | 199.236 | 19.097 | 5.512 | 1.849; 1.769; 1.235; 1.118; 1.266 | 1.266 | 1.118 | 1.849 | 0 |
| ORC/GZIP | 7 651 240 | 197.093 | 16.013 | 1.584 | 0.982; 0.983; 0.906; 0.902; 0.893 | 0.906 | 0.893 | 0.983 | 0 |
| ORC/ZSTD | 7 651 240 | 203.015 | 14.495 | 1.037 | 0.780; 0.846; 0.755; 0.771; 0.847 | 0.780 | 0.755 | 0.847 | 0 |

Parquet и ORC — колоночные форматы, а GZIP и ZSTD — разные алгоритмы сжатия внутри файлов. При одном формате GZIP дал меньшие файлы, ZSTD сократил время записи; время чтения зависело и от формата. На этом запуске меньше всего места занял **Parquet/GZIP** (193.836 МБ); самая низкая медиана Q10 была у **ORC/ZSTD** (0.780 с). Эти числа показывают только мой локальный стенд: кэш и фоновые процессы могут менять время. Во всех четырёх наборах Q10 совпал с контрольным по 20 строкам.

## 6. Lakehouse, schema evolution, time travel и Superset

Я храню файлы в S3-совместимом RustFS, Lakekeeper хранит Iceberg-метаданные, а Trino выполняет SQL. Такое разделение даёт снапшоты и чтение старой версии таблицы. Для одного `sf1` можно было бы использовать и обычную БД, но здесь я проверила именно работу файлов, каталога и SQL-движка вместе.

На отдельной `silver.lab.schema_evolution_demo` я сначала вставила строку `(1, before change)`, затем добавила столбец `source_tag`, переименовала `note` в `description` и вставила вторую строку с новым столбцом. ID снапшота перед изменениями — **4723588882722667086**. Чтение `FOR VERSION AS OF` вернуло **1 строку** и старые столбцы `id`, `note`; текущая версия вернула **2 строки** и столбцы `id`, `description`, `source_tag`. Gold я не меняла.

Я подключила Superset к Trino через `trino://student@trino:8080/bronze` и выполнила запрос SQL Lab `SELECT custkey, name, nationkey FROM bronze.lab.customer ORDER BY custkey LIMIT 10`. Он вернул 10 строк: [снимок SQL Lab](evidence/superset-sql-lab-bronze-customer.jpg) показывает запрос и таблицу. ## 7. Выводы

Я загрузила полный `sf1` в Bronze и получила из него Silver и Gold для Q10. Gold совпал с прямым запросом по всем 20 клиентам, а проверки данных не нашли ошибок.
